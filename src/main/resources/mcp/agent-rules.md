# Pohr MCP: правила работы агента со скриптами

Ты подключён к MCP-серверу Pohr (`serverName: pohr`). Его инструменты видны как
`mcp__pohr__*`. Они дают доступ к клиентским скриптам Pohr (чтение, история,
авторство, создание, правка, бэкапы, откат), к Xray-конфигам, к отчётам об
ошибках скриптов и к диагностике сервера.

Эти правила дополняют `scripts.md` — контракт клиентских скриптов Pohr.
Полный текст контракта возвращает инструмент `mcp__pohr__pohr_rules`.
Если правило из этого файла противоречит «здравому смыслу» — правило важнее.

Если в текущей сессии нет инструментов `mcp__pohr__*` (MCP не подключён или
отключён), просто игнорируй весь этот блок — он не относится к задаче.

## 1. Первый шаг в каждой сессии

Перед первой правкой скрипта вызови `mcp__pohr__pohr_rules` и прочитай контракт.
Не полагайся на память: контракт и правила могут обновиться на сервере.

## 2. Инструменты

| Инструмент | Назначение |
|---|---|
| `pohr_rules` | Полный контракт `scripts.md` + эти правила |
| `scripts_list` | Список скриптов: версия, автор, hash, зависимости, флаги |
| `scripts_read` | Содержимое активной или конкретной версии + метаданные |
| `scripts_history` | Все версии: версия, источник, автор, дата, note, snapshot |
| `scripts_create` | Создать новый скрипт (файл + запись в каталоге + версия 1.0) |
| `scripts_update` | Заменить содержимое; можно передать `expectedHash` и `note` |
| `scripts_update_meta` | Изменить displayName/description/platform/accessLevel/entrypoint/enabled/sortOrder |
| `scripts_bump_major` | Поднять мажорную версию (файл не меняется) |
| `scripts_rollback` | Откатить на версию из истории (создаётся новая минорная версия) |
| `scripts_backup` | Ручной бэкап текущего содержимого в `.history/` |
| `scripts_backups` | Список бэкапов скрипта |
| `scripts_restore_backup` | Восстановить содержимое из файла бэкапа |
| `scripts_validate` | Проверить содержимое по чек-листу контракта |
| `scripts_reseed` | Вернуть встроенную (bundled) версию скрипта |
| `scripts_delete` | Удалить скрипт (только с `confirm: true`) |

### Xray-конфиги

| Инструмент | Назначение |
|---|---|
| `xray_configs_list` | Список конфигов: id, имя, активность, hash, размер |
| `xray_config_read` | Сохранённый `content` + hash + материализованный вид активного |
| `xray_config_validate` | JSON + `xray run -test`, ничего не сохраняет |
| `xray_config_create` | Новый неактивный конфиг (с валидацией) |
| `xray_config_update` | Правка конфига; `expectedHash` защищает от перезаписи |
| `xray_config_activate` | Сделать активным в БД и материализовать файл |
| `xray_config_apply` | Проверить и перезапустить Xray (`confirm=true`) |
| `xray_status` | Запущен ли Xray, версия, активный конфиг, хвост лога |

### Отчёты скриптов (тикеты)

| Инструмент | Назначение |
|---|---|
| `script_reports_list` | Список отчётов с фильтрами `status`, `script`, `sinceHours`, `limit` |
| `script_reports_read` | Полный текст отчёта |
| `script_reports_set_status` | `NEW` / `IN_PROGRESS` / `RESOLVED` (без удаления) |
| `script_reports_stats` | Всего, по статусам, за 24 ч, топ скриптов |

### Диагностика

| Инструмент | Назначение |
|---|---|
| `server_status` | Процессы, CPU/RAM, трафик, EU-ноды, активный конфиг |
| `logs_tail` | Хвост лога `xray` / `telemt` / `nginx` / `caddy` |
| `traffic_overview` | Трафик за сегодня, активные соединения, топ клиентов |
| `nodes_list` | Статус EU-нод и туннелей |

Инструменты возвращают JSON. Ошибка приходит с `isError: true` и текстом
`Ошибка: ...` — не игнорируй её и не повторяй вызов без исправления причины.

## 3. Обязательный workflow

### 3.1 Правка существующего скрипта

1. `scripts_list` — убедись, что имя и платформа совпадают.
2. `scripts_read` — получи `content`, `hash`, `version`, `changedBy`.
3. `scripts_history` — посмотри, кто и что менял последним.
4. Если правка рискованная (много строк, несколько файлов, rollback-план) —
   `scripts_backup` с `note`.
5. Сформируй новый текст. Правь минимально, сохраняй стиль и структуру.
6. `scripts_validate` — передай `name` и новый `content`; исправь errors.
7. `scripts_update` — передай `name`, `content`, `expectedHash` из шага 2
   и `note` с кратким описанием изменения.
8. `scripts_history` или `scripts_read` — проверь, что новая версия активна,
   автор и note записались.

Если `scripts_update` вернул ошибку про hash — скрипт изменили между шагами
2 и 7. Перечитай `scripts_read`, влей свою правку в новое содержимое и
повтори. Никогда не перезаписывай вслепую.

### 3.2 Новый скрипт

1. `scripts_create` — имя по шаблону `{platform}-{purpose}.{ext}`, содержимое,
   `displayName`, `platform`, `accessLevel` (`PUBLIC` для клиентских,
   `ADMIN` для серверных), `entrypoint` при необходимости.
2. `scripts_validate` — проверь errors/warnings.
3. Если ошибся в содержимом — `scripts_update` с `expectedHash`.

### 3.3 История и откат

- `scripts_history` — все версии, включая автора и note.
- `scripts_rollback` — откат на версию из истории; создаётся новая минорная
  версия, старая история сохраняется.
- `scripts_backups` + `scripts_restore_backup` — работа с ручными бэкапами
  `.history/`.
- `scripts_bump_major` — только когда меняется контракт/поведение скрипта,
  а не при обычной правке.

### 3.4 Метаданные

`scripts_update_meta` меняет только каталог, не содержимое. Меняй
`accessLevel` и `entrypoint` осознанно: `PUBLIC`-скрипт можно скачать
обычному пользователю, `entrypoint` попадает в список установки на `/home`.

### 3.5 Правка Xray-конфига

1. `xray_configs_list` — найди конфиг и убедись, какой из них активен.
2. `xray_config_read` — получи `content`, `hash`, `updatedAt`. Правь именно
   `content` (сохранённую форму), а не `materialized`: clients, api, stats,
   routing и EU-outbound генерируются сервером.
3. `xray_config_validate` — прогони новый JSON через проверку.
4. `xray_config_update` — передай `content`, `expectedHash` из шага 2 и
   `description`/`realityPublicKey` при необходимости.
5. `xray_config_activate` — только если нужно сделать конфиг активным.
6. **`xray_config_apply` — только после явного согласия пользователя.**
   Он перезапускает Xray и на несколько секунд рвёт все клиентские
   соединения. Без `confirm=true` инструмент откажет.

Если `xray_config_update` вернул ошибку про hash — конфиг изменили между
чтением и записью. Перечитай `xray_config_read`, влей правку в новый
`content` и повтори. Никогда не сохраняй конфиг «вслепую».

Если `xray -test` не проходит — не используй `force`, пока не поймёшь
причину: сломанный конфиг применяется только после `xray_config_apply`,
но сохранять заведомо нерабочий конфиг в БД всё равно нельзя.

### 3.6 Отчёты об ошибках скриптов

1. `script_reports_list` — посмотри новые и «в работе»; при необходимости
   отфильтруй по `script` и `sinceHours`.
2. `script_reports_read` — прочитай полный текст и stage.
3. Найди причину в коде скрипта через `scripts_read`/`scripts_history`.
4. После исправления — `script_reports_set_status` в `RESOLVED` (не удаляй
   отчёт: удаление остаётся действием человека в админке).
5. Если ошибка воспроизводится — предложи правку скрипта по workflow 3.1.

### 3.7 Диагностика

`server_status`, `logs_tail`, `traffic_overview`, `nodes_list` — read-only.
Начинай разбор инцидента с `server_status` и `logs_tail`, а не с догадок.
Помни: `logs_tail` хранит только строки с момента старта процесса.

## 4. Контракт клиентских скриптов (кратко)

Полная версия — в `pohr_rules`. Ниже — то, что агент обязан помнить всегда.

### 4.1 Плейсхолдеры

- `{{__VERSION__}}` — версия скрипта; её подставляет сервер.
- `{{BASE_URL}}`, `{{TOKEN}}`, `{{SUBSCRIPTION_URL}}`, `{{RULES_URL}}`,
  `{{SCRIPTS_BASE_URL}}` — параметры подписки.
- URL других скриптов — только через `{{SCRIPTS_BASE_URL}}/name/raw`.
- Никогда не заменяй плейсхолдер на литерал и не пиши версию в исходник.

### 4.2 Каркас

- `.bat` — только загрузчик `.ps1`; три аргумента `-RootName`,
  `-RootVersion`, `-Ps1Version`; не анализирует содержимое.
- `.ps1` — `param(...)`, `$ErrorActionPreference = "Stop"`, загрузка
  `pohr-utils.ps1` с чтением `X-Pohr-Script-Version`, вся логика в `try/catch`,
  `$Stage` перед каждым шагом, `Send-PohrSync` в конце, `Send-PohrErrorReport`
  в `catch`.
- `.sh` — `set -euo pipefail`, `trap ... ERR`, версия через `curl -D -`.

### 4.3 Логирование

Только `Write-PohrInfo/Ok/Warn/Error/Debug`, не `Write-Host`. Каждое
логическое действие — одна строка.

### 4.4 Идемпотентность и транзакции

- Повторный запуск не должен ломать систему.
- Перед изменением чужого файла — `New-PohrPristineBackup` один раз,
  `New-PohrTimestampedBackup` каждый запуск, `Start-PohrTransaction` /
  `Complete-PohrTransaction`.
- Чужие подписки/конфиги не трогать; наша подписка — `remarks = "Pohr"`.

### 4.5 Кодировки

Сервер нормализует: `.sh` — LF, `.bat/.cmd/.ps1` — CRLF, `.ps1` — UTF-8 BOM
при отдаче. В MCP передавай обычный текст; не добавляй BOM вручную.

### 4.6 Антипаттерны

- Хардкод URL, токена, версии.
- `Write-Host` вместо `Write-Pohr*`.
- Молчаливый `catch` без error-report.
- Забытый `sync`.
- `curl | bash` как способ доставки.
- Чтение `{{__VERSION__}}` как «магической» переменной PowerShell.

## 5. Правила взаимодействия с пользователем

1. Не используй `pwsh`, `write`, `edit` или другие файловые инструменты для
   изменения скриптов на сервере. Только MCP-инструменты Pohr — они ведут
   версии, авторство и бэкапы.
2. Не переписывай скрипт целиком, если достаточно точечной правки. Сохраняй
   существующие комментарии, порядок секций и стиль.
3. Перед удалением, `reseed` или массовым откатом спроси подтверждение
   у пользователя. `scripts_delete` вызывай только с `confirm: true` и
   только после явного согласия.
4. Всегда указывай в `note`, что и зачем изменено. Это увидит админ в UI.
5. После правки сообщи: имя скрипта, старую и новую версию, автора, что
   изменилось и нужен ли перезапуск/повторная установка у клиентов.
6. Если инструмент вернул ошибку — покажи её пользователю и остановись.
   Не пытайся обойти MCP прямым доступом к файлам.
7. Не выводи MCP-токен и не проси пользователя присылать его в чат.
8. Не трогай файлы на сервере напрямую. Xray-конфиги меняются только через
   `xray_config_*`, клиентские скрипты — только через `scripts_*`, а клиентские
   конфиги на машинах пользователей — только клиентским скриптом.
